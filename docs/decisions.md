# Recorded Decisions

This file records settled decisions that affect more than one planning document.

## Delivery order

- Phase 1 is organizer-first: create and manage open-mic series, create and operate events, manage rosters, and publish organizer-owned photos and video links.
- Performers can sign up, browse open-mics and events, and register in Phase 1.
- Phase 1 public surfaces are read-only for visitors and include the home, profile, open-mic, event, and registration pages.
- Performer-authored content, comments, reviews, reactions, private messaging, follows, and social discovery are deferred until later phases.

## Handles

- Profiles and open-mic series share one global handle namespace.
- Canonical handles preserve owner-selected casing; lookup and uniqueness are case-insensitive.
- Case-only changes are allowed without limit, do not create redirect history, and redirect previous casing to the new canonical URL.
- Changes to any non-case character use the normal rename restrictions: 30-day redirect, 30-day quarantine, and auto-reclaim afterward.
- Owners retain the original guest registration provenance when a registration is claimed or later attributed to a profile.

## Guest Registrations

- Guest registrations may be claimed at any time during or after the event.
- Claiming is explicit and requires a verified email match.
- Adoption of a claiming profile is an explicit public-attribution choice and may be changed later by the registration owner.
- The claim request identifies the adopted profile explicitly (`adopted_profile_id`), since an account may own more than one performer profile.
- A duplicate guest registration is defined as a second row for the same event with the same verified contact email; unverified/pending rows do not block others until confirmed. Enforced by a partial unique index on `(event_id, lower(contact_email))` where `email_verified_at IS NOT NULL`.
- A registration claim is atomic: the first successful claim wins, and a losing concurrent claim attempt fails explicitly with `409` rather than silently overwriting or duplicating attribution.
- Media consent can be revoked after registration, but revocation is future-only: it blocks new media publication under that registration and is not retroactive against media already published. `Registration.media_consent_updated_at` records when consent last changed, for audit purposes.
- Guest registration submission is rate-limited per source (e.g. per IP) to deter abuse; exceeding the limit returns `429`.

## Forms and location picker

- React Hook Form + Zod is the standard for every form in `apps/web`, including forms that don't touch location (e.g. the profile editor). Shared per-form Zod schemas live near each page; shared cross-form pieces (e.g. `baseLocationFieldsSchema`) live in `apps/web/src/features/location.ts`.
- The venue/event location fields (map, address, latitude/longitude) are implemented once as a reusable `LocationPicker` component (`apps/web/src/components/location/`) plus a `useGeocoding` hook, embedded via any form that collects a location — today the OpenMic and Event forms, and any future form that needs one.
- Map rendering uses Leaflet + react-leaflet with public OpenStreetMap raster tiles (no API key required for the map itself), chosen over MapLibre/Google/Mapbox/OpenLayers per the comparison in [research/open-mic-map-location-picker.md](research/open-mic-map-location-picker.md).
- Geocoding (address → coordinates and reverse) uses LocationIQ, accessed only through a backend proxy (`GET /geocoding/search`, `GET /geocoding/reverse` — see [architecture/api-design.md#geocoding](architecture/api-design.md#geocoding)); the LocationIQ API key never reaches the browser.
- The backend proxy throttles outgoing LocationIQ calls to stay within the shared free-tier rate limit across all concurrent users, and returns a distinct `GEOCODING_RATE_LIMITED`/`GEOCODING_UNAVAILABLE` error the frontend can detect.
- On rate-limiting or provider failure, the frontend disables the address-lookup assist for the rest of the session and logs the event through a pluggable reporter (console-only for now; swappable for real telemetry later without changing call sites). The map's draggable pin and the always-present numeric latitude/longitude inputs keep working regardless — the assist is a progressive enhancement, never a requirement to submit a location.

## Media

- Organizer-owned media `source_url` is validated server-side: photos must be objects in the platform's own S3 media bucket (via the upload-url flow); videos must link to an allowlisted host (`youtube.com`, `youtu.be`, or `vimeo.com`). Arbitrary hosts are rejected.

## Infrastructure

- **Infrastructure authority:** AWS CDK (TypeScript) is the infrastructure boundary. Code lives under `infra/` as its own package (own `package.json`/`tsconfig.json`, CommonJS — deliberately not part of the root `"type": "module"` workspace). `bin/infra.ts` is the CDK app entry; each bounded concern gets its own stack class under `infra/lib/` (e.g. `EmailStack`). This decision supersedes the older EC2-oriented infrastructure narrative until those architecture pages are rewritten.
- **API compute:** ECS Fargate (not EC2), because the API serves long-lived SSE connections (`GET /api/notifications/stream`), which rules out Lambda-behind-API-Gateway without a WebSocket re-architecture. Fargate keeps a persistent Node process without server patching/PM2/systemd.
- **Email:** SES, invoked only through an SQS queue + a Lambda consumer (never called synchronously from the API). The API's `EmailAdapter` (`apps/api/src/email/`) enqueues a JSON message; the Lambda in `infra/lib/lambda/email-sender/` sends it via SESv2. Failed sends retry via SQS and land in a dead-letter queue after 3 attempts. This part matches the original `infrastructure.md` design and is unchanged.
- **Cognito/Amplify:** Cognito remains the managed auth provider. The frontend uses the Amplify **client SDK only** for Auth (`aws-amplify/auth`). Frontend hosting, Cognito, S3, and all other AWS resources are provisioned via CDK.
- **CI/CD:** GitHub Actions with OIDC federation to AWS (no long-lived IAM access keys stored as repo secrets) for both application deploys and any future `cdk deploy` step.
- **Environments:** CDK stacks are namespaced per environment (`OpenMicEmailStack-dev`, `-staging`, `-prod`) via an `environmentName` context value/`OPENMIC_ENVIRONMENT` env var, starting in one AWS account; a harder account-per-environment split is deferred until team size or compliance needs justify the added overhead.
- Deployment/validation status: `cdk synth` has been run locally to validate the stack; nothing has been deployed to AWS yet (no bootstrap, no real resources exist).

## Retention

- Phase 1 soft-deletable records (profiles, open-mics, events, registrations, media) use one uniform window: 30 days recoverable, then hard-deleted by the purge job. This matches the handle redirect/quarantine cadence already in place.

## API Contract

- `openapi.yaml` is reduced to the Phase 1 executable contract. Reviews, comments, reactions, private messaging, suggestions, notifications, follows, multi-admin collaboration roles, public map discovery, and the legacy slug system are removed from the contract (not the product) and tracked as deferred surface in [architecture/api-design.md](architecture/api-design.md).
- Profile and open-mic updates use `PATCH` with a genuinely partial request body, not `PUT` with a full-replacement body.
- `Handle.status` and `Availability.reason` use the six-state model from [6-open-mic-vanity-urls.md](6-open-mic-vanity-urls.md): `current`, `redirect`, `quarantined`, `reserved`, `available`, `tombstoned`.
- The public vanity resolver (`GET /@:handle`) is intentionally outside `openapi.yaml`; it is served by Fastify directly, outside the `/api` base.

## Milestone 0 contract reconciliation

- **Event update/delete path:** the implementation moved to the flat `/events/{id}` path (`PATCH`/future `DELETE`), matching `openapi.yaml`, rather than keeping the nested `/open-mics/{id}/events/{eventId}` path the code had drifted to. The nested `GET /open-mics/{id}/events/{eventId}` read route is retained (it is not the mismatch that was flagged) alongside the flat `GET /events/{id}`; both resolve the event by UUID or `public_code`. `openapi.yaml`'s `updateEvent` operation is `PATCH`, not `PUT`, for the same partial-update reason as profiles/open-mics.
- **`/auth/sign-up`, `/auth/sign-in`, `/auth/refresh-token`:** removed from `openapi.yaml`. No frontend code called them; the browser talks to Cognito directly through Amplify. `GET /auth/profile` (implemented, aliases `GET /me`) is unaffected and remains.
- **`PUT /registrations/{id}` → `PATCH /registrations/{id}`:** changed for the same partial-update reason as profiles/open-mics/accounts. `PUT /accounts/{id}` (unimplemented, Milestone 1) is also corrected to `PATCH` in `openapi.yaml` while making this pass, since it is a genuinely partial update (`preferred_language`, `display_name`, `city`) and not a full-resource replacement. `PUT /accounts/{id}/current-profile` is intentionally left as `PUT`: it replaces a single pointer value wholesale, not a partial field set.
- **Media, reserved-handle admin, `PATCH /accounts/{id}`, edit-token rotation:** left as documented-but-unimplemented in `openapi.yaml`, each already assigned to its milestone (5, 4, 1, 3 respectively per [IMPLEMENTATION-PLAN.md](../IMPLEMENTATION-PLAN.md)). No removal or new implementation in this pass.

## Milestone 1 authentication

- **ID token, not access token, is the bearer token `AuthVerifier` verifies.** [IMPLEMENTATION-PLAN.md](../IMPLEMENTATION-PLAN.md) originally said "access-token verification"; [5-open-mic-frontend-architecture.md](5-open-mic-frontend-architecture.md) says the client attaches the Cognito ID token. These conflicted; resolved in favor of the ID token, because only the ID token carries the verified `email` claim account provisioning needs, and `IMPLEMENTATION-PLAN.md` has been updated to match. The verifier rejects any token whose `token_use` isn't `id` (including access tokens) alongside malformed/expired/wrong-issuer/wrong-audience tokens.
- **Account provisioning is idempotent-upsert-on-first-request, not OAuth-callback/referral-attributed.** `architecture/data-model.md` and `architecture/api-design.md` describe a richer OAuth-callback provisioning flow tied to referral capture via a signed `state` value; that flow is scoped to Milestone 3 (referrals). Milestone 1's `findOrCreateAccountByCognitoId` provisions an account on first successful verification via `INSERT ... ON CONFLICT (cognito_id) DO UPDATE ... RETURNING`, with no referral attribution yet.
- **`is_platform_admin` is always read from the `accounts` table**, never trusted from a JWT claim, per `architecture/data-model.md` — Cognito ID tokens can remain valid up to an hour, and a revoked admin must lose access sooner than that.
- **Profile preferences and mandatory onboarding (item 6 redesign):** `IMPLEMENTATION-PLAN.md` originally described account-level theme/color-mode preferences for `PATCH /accounts/{id}`, but `architecture/data-model.md`'s `Accounts` table has no such columns (only `Profiles.theme_name`). Resolved by keeping `theme_name`/new `color_mode` on `Profiles` (added via migration `010_profile_color_mode`), leaving `PATCH /accounts/{id}` scoped to `display_name`/`city`/`preferred_language` only (matching `AccountUpdateRequest`), and adding a mandatory frontend onboarding step (performer vs. organizer, plus theme/color-mode) that runs whenever a signed-in account has zero profiles, reusing `POST /profiles`. The same theme/color-mode picker is reusable at any profile-creation time, not just onboarding. See `architecture/data-model.md`'s "Onboarding and profile-scoped preferences" note.
- **Organizer route-level ownership check (item 8):** auditing the pre-existing per-page `isOrganizer` checks found they already relied on real server responses (`/me/permissions` and the account's own `/accounts/{id}/profiles` list) rather than any locally-trusted assumption, so no security fix was required for series/event listing pages. However, the open-mic and event edit forms (`OpenMicFormPage`, `EventFormPage`) checked only the role-level `profiles:manage` permission, not whether the specific resource being edited (`owner_profile_id`) belonged to the active organizer profile — an organizer could load another organizer's edit form by guessing/URL-sharing an id, though the API itself already rejected the eventual mutation. Both forms now additionally gate on `owner_profile_id === activeProfile.id` before rendering. The duplicated `isOrganizer`-check logic across five pages was also consolidated into one `useOrganizerProfile()` hook in `features/organizer.ts`.
- **`display_name`/`profile_name` defaults must never trust `cognito:username`.** A production bug surfaced a raw Cognito `sub` GUID as an account's `display_name` and, downstream, as the onboarding-created profile's `profile_name`. Root cause: `cognito-verifier.ts`'s display-name fallback used `payload['cognito:username']`, which for this user pool's email-alias sign-in configuration (no `name` attribute collected at hosted-UI sign-up) equals the raw `sub`. Fixed by dropping that fallback in favor of the email's local part (`payload.email.split('@')[0]`), and by making `OnboardingPage` always require the user to confirm/edit a suggested profile name and a suggested handle (with the same live availability check as `OpenMicFormPage`/`EventFormPage`, via `useHandleAvailability`) rather than silently submitting an unconfirmed default — a defense against any future bad default from any source. `POST /profiles` already accepted an optional `handle`; onboarding now always supplies one.
- **The organizer dashboard's "my series" list needs its own endpoint, not the public directory query with an ad hoc filter.** A production bug: after creating a series (default `status='draft'`), the organizer's own dashboard (`OrganizerSeriesPage`, `OrganizerEventsPage`) couldn't see it — the newly created series page rendered blank. Root cause: `useOrganizerOpenMics` called the public `GET /open-mics?owner_profile_id=...`, but `owner_profile_id` was never a documented parameter of that endpoint — it was an undocumented ad hoc addition that still inherited the public directory's `status NOT IN ('draft','ended')` filter (intentional and correct for the public directory itself; see `architecture/api-design.md`'s "Directory search & map endpoints" section). Fixed by adding an authenticated `GET /me/open-mics?owner_profile_id=...` endpoint, following the existing `GET /me/permissions`/`GET /me/registrations` account-scoped pattern: it verifies the caller owns the given profile and returns every non-deleted series regardless of status. The frontend's `useOrganizerOpenMics` now calls this endpoint instead, fixing both dashboard surfaces at once.
- **Handle auto-suggestion and submit-gating must not silently freeze/block on transient async state.** Two related bugs surfaced from real usage of `OpenMicFormPage`/`OnboardingPage`: (1) the auto-suggested handle stopped updating after the first keystroke in the name field, traced to an effect that both watched and conditionally overwrote the same RHF-managed field gated on `dirtyFields.handle` — a fragile, timing-dependent pattern; fixed by tracking "user has manually edited the handle" with a plain `useRef` set only from the handle input's own `onChange`, decoupled from RHF's internal dirty-tracking. (2) both forms disabled their submit button whenever the async handle-availability check hadn't resolved to exactly `'available'`, including transient `'checking'`/`'idle'` states, so any network hiccup silently and permanently blocked submission; fixed by only blocking on confirmed-bad states (`'unavailable'`/`'invalid'`) and trusting the server's existing `HANDLE_UNAVAILABLE` error response as the final authority, consistent with treating the server as authoritative over client-side hints elsewhere in the codebase.



- Phase 1 SSE is scoped to exactly one stream: the organizer/assistant event-roster stream, `GET /events/{id}/roster/stream`. There is no general account-level or notifications stream in Phase 1 (`/notifications*` remains deferred, see [architecture/api-design.md](architecture/api-design.md#deferred-later-phase-api-surface)); [5-open-mic-frontend-architecture.md §6](../docs/5-open-mic-frontend-architecture.md) is scoped to match.
- **Authentication:** `EventSource` cannot send an `Authorization` header. The client first calls authenticated `POST /events/{id}/roster/stream-token` (organizer/assistant of that event only) to obtain a single-purpose `stream_token` valid for 5 minutes, then opens `GET /events/{id}/roster/stream?stream_token=...`. Raw bearer tokens are never placed in a URL.
- **Event names:** `registration.created`, `registration.updated`, `performance.created`, `performance.updated`, `performance.deleted`, `performance.reordered`.
- **Ordering and missed-event recovery:** every emitted event carries a monotonically increasing `id:` field (per event scope) so the browser's native `Last-Event-ID` header drives resume-after-reconnect. If the server can't satisfy a given `Last-Event-ID` (expired/unknown, e.g. after a deploy), it sends a `resync_required` event instead of replaying; the client responds by refetching `GET /events/{id}/registrations` in full rather than assuming partial replay is safe.
- **Heartbeat:** the server sends an SSE comment ping every 15 seconds to keep the connection alive through intermediary proxies/load balancers and to let the client detect a silently-dead connection.
- **Multi-instance fan-out:** the API runs as multiple ECS Fargate tasks, so an in-process event emitter cannot reach a connection held by a different task. The server uses PostgreSQL `LISTEN/NOTIFY` (channel keyed by event id) so any task holding the SSE connection for that event is notified regardless of which task handled the write, without introducing a separate message broker for Phase 1.
- **Reconnect:** the client uses exponential backoff capped at 30 s, per [5-open-mic-frontend-architecture.md §6](../docs/5-open-mic-frontend-architecture.md).
- This contract is defined now (Milestone 0) but not implemented; Milestone 2 either implements it or, if descoped, Milestone 2 must make polling the explicit fallback rather than leaving a placeholder claim (see IMPLEMENTATION-PLAN.md Milestone 0 item 3).

## Milestone 2 event lifecycle

- **Event soft-delete/recover implemented as flat per-table columns, not the unified `Deletions` journal table.** `architecture/data-model.md` describes an eventual unified deletions/recycle-bin journal, but no migration for it exists yet, and the already-shipped `performances` soft-delete (Milestone 0) did not build one either. `DELETE /events/{id}` (soft delete: sets `deleted_at`, `deleted_by_profile_id`, `recovery_deadline = now() + 30 days`) and `POST /events/{id}/recover` (restore: clears those three columns, only while `recovery_deadline > now()`) follow that same narrow, per-table precedent for consistency. Building the shared journal table remains open for whenever a cross-resource recycle-bin UI is actually needed.
- **Close/reopen registration needed no new endpoint.** It's already fully covered by the generic `PATCH /events/{id}` endpoint's nullable `registrations_closed_at` field; `EventFormPage` already has a "Close registrations now" action, and clearing the field reopens registration. No separate `close`/`reopen` operation was added.
- **Organizer roster (item 2) reuses the existing per-registration performance CRUD rather than adding new endpoints.** `POST /performances`, `PUT /performances/{id}`, `DELETE /performances/{id}` (Milestone 0) already cover create/edit/soft-delete with organizer-ownership checks; the only gap was listing. `GET /events/{id}/registrations` (organizer-only) now embeds each registration's `performances` (including organizer-only `notes`) via a batched lookup, avoiding an N+1 query per roster row. The frontend `EventRosterPage` (`/dashboard/series/{seriesId}/events/{eventId}/roster`) renders provenance badges (pending/verified/kiosk, derived the same way as the server's "publicly visible" rule), capacity/closure summary, filters, and per-performance sequence/status/notes controls (a plain number input for explicit sequence editing, per the plan's "sequence... or explicit sequence editing" alternative — no drag-and-drop reorder was built).
- **Kiosk registration (item 3) needed no backend changes.** `POST /events/{id}/registrations` already fully supported `organizer_supervised: true` + `submission_channel: 'kiosk'` (Milestone 0): it requires only `performer_name` (no contact email), sets `verification_method: 'organizer_kiosk'` and an immediate `email_verified_at`, and skips the confirmation-email flow entirely. The new frontend `KioskPage` (`/dashboard/series/{seriesId}/events/{eventId}/kiosk`, linked from the roster page's "Open kiosk" button) is a dedicated dark, high-contrast, large-touch-target form that requires only the performer's name, resets and refocuses itself right after each successful add (with a brief on-screen confirmation, no page reload), and surfaces closure/capacity/duplicate/forbidden errors with kiosk-specific copy.
- **Roster redesign: performances are no longer a separate concept from performers in the UI.** Every registration now gets its first `Performances` row auto-created in the same transaction as the registration itself (status `present` for kiosk sign-ups, `registered` otherwise), so a "performer card" on the roster page is really just a performance row with its registration's contact/provenance info attached — organizers never see a bare registration with zero performances. `Performances.status` grew from 4 values to a 7-state lifecycle: `registered -> present -> scheduled -> performing -> performed`, plus `no_show`/`cancelled` as manual overrides from any state. Four new nullable timestamp columns (`checked_in_at`, `scheduled_at`, `started_at`, `finished_at`) are stamped automatically (server clock only, never client-supplied) whenever a row's status is set to the corresponding value, on both create and update. A performer doing a second set is **always a brand-new `Performances` row** (never the old row looping backwards), typically starting at `present` since they're already known to be at the venue — this preserves full history of every set played instead of overwriting it. The roster page displays a Kanban board (one column per forward state) on large screens and a single filterable list on small screens, with one primary action button per card (Check in / Schedule / Start / Finish) that always maps to exactly one status write.
- **Kiosk exit PIN: backup PIN is now server-side per series; one-time PIN is still organizer-chosen each session.** The kiosk page runs fullscreen and requires a PIN to exit back to the roster/dashboard. Each time the organizer opens the kiosk they choose their own fresh one-time PIN for that session (no longer randomly generated) — it's never persisted anywhere, just held in memory for the lifetime of that kiosk session. The backup PIN (used only if the organizer forgets the one-time PIN they picked) is configured per open-mic series and stored server-side (`open_mics.kiosk_backup_pin_hash`, client-hashed with SHA-256 before it's ever sent — the API never sees or returns a plaintext PIN), via dedicated `GET`/`PUT /open-mics/:id/kiosk-backup-pin` and `POST /open-mics/:id/kiosk-backup-pin/verify` endpoints (owner-authenticated; the hash is deliberately excluded from `serializeOpenMic`'s output, including the public `GET /open-mics/:id`). This replaced the original per-device `localStorage` backup PIN so it survives across devices/browsers running the same series' kiosk. It remains a device-convenience lock, not an account-security boundary — any signed-in organizer can still independently open their own kiosk session for the same event with their own one-time PIN.
- **Stopping an event auto-marks unregistered performers as no-show and closes registrations; restarting does not undo either side effect.** `Events.running` (already in the schema, previously unused by any endpoint) now drives real behavior: `PATCH /events/{id}` with `running: false` (transitioning from `true`/unset) runs the event update, sets `registrations_closed_at` to the server time, and performs the bulk `Performances` transition — every performance still in `registered` status for that event becomes `no_show` — inside a single DB transaction (`markUnregisteredAsNoShowForEvent` in `performances/repository.ts`). Only `registered` rows are touched; `present`/`scheduled`/`performing`/`performed`/`no_show`/`cancelled` performances are left alone. Setting `running` back to `true` ("restart", e.g. to undo an accidental stop) is a plain field update with no reverse side effect — registrations remain closed and no-shows created by a stop are not automatically un-done, since there's no reliable way to distinguish "was already a no-show" from "became one because the event stopped." An organizer can still manually reopen registrations by clearing `registrations_closed_at` and manually move a no-show performer back to `present` via the existing performance-update endpoint. A `PATCH /events/{id}` handling `event.updated` notification is now emitted over the roster SSE stream so open roster views refresh when another tab/device stops or restarts the event.
- **Live roster updates (item 4) use PostgreSQL `LISTEN`/`NOTIFY`, not a persisted event log.** `POST /events/{id}/roster/stream-token` mints a 5-minute HS256 JWT (new `STREAM_TOKEN_SECRET` config value, with an insecure dev/test default) because `EventSource` cannot send an `Authorization` header. `GET /events/{id}/roster/stream` verifies that token, then `LISTEN`s on a per-event channel (`roster_<eventId-without-hyphens>`, kept alphanumeric so the unparameterizable `LISTEN`/`UNLISTEN` statements stay injection-safe) and forwards lightweight NOTIFY payloads (event name + id only, no row data) as SSE events with an incrementing `id:`. `registrations/routes.ts` and `performances/routes.ts` call a shared `notifyRoster` helper after every create/update/delete. **No durable replay log is kept**: since NOTIFY payloads are fire-and-forget and Postgres does not retain them, any reconnecting client that sends a `Last-Event-ID` header always receives an immediate `resync_required` event (telling it to refetch `GET /events/{id}/registrations` in full) before live-tailing resumes — there is no partial/incremental catch-up. This means every reconnect (page backgrounded, laptop sleep, brief network blip) costs one full roster refetch instead of a small diff; multi-instance fan-out (ECS Fargate) works because NOTIFY is broadcast to every listening backend connection regardless of which instance handled the client's request. This was implemented without a follow-up confirmation from the user; if reconnects turn out to be frequent enough in practice for the extra refetch cost to matter, revisit with a small ring-buffer replay log per event.
- **Kanban board is restricted to board-eligible registrations; pending ones get a separate simple list, and "claimed" was dropped from roster filtering entirely.** Per explicit user direction, the roster's per-card Kanban/list only shows registrations that are verified (self-registration, `email_verified_at` set) or kiosk (`organizer_supervised`) — a registration still awaiting email confirmation isn't board-eligible yet, so its performances are excluded from the board/mobile-list data entirely rather than just filtered out visually. Pending registrations instead render in a plain "Pending confirmation" `<ul>` (`PendingRegistrationRow`: name + Details/Edit only, no move controls, no kanban card styling) shown above the board. The provenance filter bar is now `All | Pending | Verified | Kiosk` — selecting "Pending" hides the board and shows only that list; the other three filter the board itself. `claimed_by_account_id` is a separate attribution concept (which account a registration is linked to) that doesn't affect roster eligibility or lifecycle, so it was removed from `provenanceOf`/the filter bar; it's still fully readable via `GET /registrations/{id}` and the registration-edit/details modals for anyone who needs it, just not roster-facing.
- **Roster "Delete" card action added a new `DELETE /registrations/{id}` endpoint (soft-delete, organizer-only).** No such endpoint existed before this change even though `registrations.deleted_at`/`deleted_by_profile_id`/`recovery_deadline` columns were already in the schema (migration 002). It mirrors `softDeleteEvent`/`softDeletePerformance`'s 30-day recovery window exactly, and deliberately uses the stricter event-owner check rather than `assertRegistrationAccess`, since the registration's own claimed-by account should not be able to delete it — only the event's organizer (or a platform admin) can. The frontend only offers "Delete" from the Registered column's card menu (before anything else has happened to that performer), behind a confirmation modal — once someone's checked in, been scheduled, performed, or marked no-show, deleting isn't offered; "No-show" is the equivalent action for that history-preserving case instead.
- **Roster page's "Stop registrations" button reuses the existing `PATCH /events/{id}` `registrations_closed_at` field (no new endpoint), same mechanism already described above for `EventFormPage`'s "Close registrations now" action.** The organizer can reopen registrations from either surface by clearing the nullable field; the control toggles between stopping and reopening without changing existing registrations or performances.
- **Moving a performer into "scheduled" auto-assigns the next event-wide `sequence` number server-side, instead of leaving it unset.** Previously, drag/move actions only ever sent `status` in the `PUT /performances/{id}` body, so `sequence` (already `ORDER BY sequence ASC, created_at ASC` in every roster query) stayed at its create-time value/`null` for everyone — meaning "who's up next" wasn't actually deterministic across organizers/devices, it just happened to match registration order. Now, when a `PUT /performances/{id}` sets `status: 'scheduled'` and the client didn't explicitly send a `sequence`, the server computes one itself (`nextSequenceForEvent`: `MAX(sequence)` across the event's non-deleted performances, `+1`) and stores it alongside the status change. Because ordinary status-only updates never touch `sequence`, that number is carried unmodified through `performing`/`performed`, so it doubles as the eventual play-order record — matching the request that "scheduled order and performance order... could be the same column." This is a best-effort (not fully serializable) counter: two organizers scheduling different performers in the same instant could theoretically compute the same next value before either write commits; given the low concurrency of this action in practice, that race was accepted rather than adding transaction-level locking.
- **Kanban board redesign: per-column sequencing, uniform delete-cascades-to-registration, and stricter movement rules — supersedes the "event-wide sequence" and "delete only from Registered" bullets above.** Per explicit user direction, refined the roster board as follows:
  - `sequence` is now scoped per status column instead of event-wide: `nextSequenceForColumn` computes `MAX(sequence)+1` within "present" or "scheduled" only (or `1` if that column is empty), replacing the old single event-wide counter. A performance is auto-assigned a bottom-of-column sequence whenever it enters "present" or "scheduled" without an explicit `sequence` — this covers both organizer moves and kiosk sign-ups (which land at the bottom of "present"). "performing" and "performed" don't carry a meaningful sequence at all (performed order is implied entirely by `finished_at`); "registered" cards are shown in registration order. Reordering (swapping two cards' `sequence`) is now rejected by the API unless the card's current status is "present" or "scheduled" — it is no longer possible to reorder within "performed".
  - **Delete now applies uniformly to a card in any column, not just "Registered".** Deleting a performance's card soft-deletes just that `Performances` row, unless it is the registration's only remaining (non-deleted) performance, in which case the API also soft-deletes the parent `Registrations` row in the same request (the performer would need to register again for a future set). The confirmation modal's copy distinguishes these two outcomes ("delete this performance" vs. "delete the registration") based on whether the registration has other performances. The DELETE handler runs the cascade check and any cascade delete *before* sending its response (not fire-and-forget afterward), so an immediate follow-up GET from the same client can't race ahead and see stale, non-cascaded state.
  - **Movement is restricted at both ends of two columns.** Only the "scheduled" card with the lowest `sequence` (top of the queue) may transition to "performing" — enforced server-side via a `topOfScheduled` lookup, not just hidden in the UI. Only the "performed" card with the latest `finished_at` may move out of "performed" to any other status (`lastPerformed` lookup) — covering the "moved to performed by mistake" fix-up case while leaving history-preserving order intact for everyone else already performed.
  - **Two timestamp special cases were added to the "stamp on entering status" default.** "performed" -> "performing" preserves `started_at` (it's the same set resuming, not a new one) and clears `finished_at`; "performing" -> "scheduled" (moved back a stage) clears both `started_at` and `finished_at`.
  - **Event-stop cleanup was extended.** In addition to the existing "mark unregistered as no_show" behavior, stopping an event (`running: false`) now also soft-deletes any performance that never reached "performing" (`started_at IS NULL`) in the same transaction, since a valid, reportable performance requires both a start and a finish time.
  - `registration.deleted` was added to the frontend's `ROSTER_STREAM_EVENTS` list (it already existed as a server-emitted SSE event name from the original `DELETE /registrations/{id}` work, but the roster page wasn't listening for it) so other open tabs refresh when a cascade-delete removes a registration.
- **Fixed duplicate roster GET requests on every organizer-initiated change.** Every roster mutation (`useUpdatePerformance`, `useCreatePerformance`, `useUpdateRegistration`, `useDeleteRegistration`, `useDeletePerformance`, `useCloseRegistrations`, `useSetEventRunning`) already invalidated the roster query in its own `onSuccess`. But the exact same change also arrives back over the roster's own SSE stream a moment later (Postgres NOTIFY is broadcast to every listener, including the tab that made the change), which invalidated the query a *second* time — two GETs for one edit. Fixed by having each mutation mark its target query key as "self-caused" in `onMutate` (before the request round-trip, since the NOTIFY can race ahead of the HTTP response) via a small in-memory `Map` (`markSelfCausedChange`/`consumeSelfCausedChange` in `features/organizer.ts`, keyed by `roster:<eventId>`/`event:<eventId>`, one-shot with a 5s expiry); the SSE handler consumes that mark instead of invalidating when it sees the matching event. `resync_required` and the on-error reconnect catch-up path deliberately bypass this suppression (via a separate always-unconditional `invalidateRoster`), since those exist specifically to catch up on changes this tab might not already know about.
