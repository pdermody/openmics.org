# Recorded Decisions

This file records settled decisions that affect more than one planning document.

## Public landing-page details and attendance

- Public series and event landing pages retain compact summaries and link to separate More details pages (`/@:handle/details` and `/@:handle/events/:eventId/details`). Both use non-interactive fact badges, followed by plain venue/city text and More details in the same wrapping row; venue labels are not links. A resource-specific back control returns to the landing page. Direct access, canonical casing and return browsing state are preserved.
- Series registration actions appear beside the highlighted running/next event only when an eligible registration event exists, not beside the header facts. Featured-strip scroll arrows appear only in directions with additional off-screen media and disappear when all items fit.
- More details uses a story-led "night at a glance" layout: organizer introduction, activity/tag badges and stage policies alongside a practical visit card. Mobile stacks the same reading order. Descriptive claims are organizer-supplied, never inferred; location anchors, map consent and public-data boundaries are unchanged.
- Show map opens a roomy venue-map modal, capped on desktop and bounded by the small visible viewport with outer clearance and safe-area allowances at all widths (including tablets using desktop styling); mobile is top-anchored. Browser controls must not obscure its bottom. It supports mouse-wheel zoom, close/Escape dismissal and focus restoration. The map fits the remaining modal space and refreshes its measurements on resize; unusually long header content scrolls within the dialog rather than clipping. The details page remains a separate page; only the map is modal. Address and driving directions remain available without opening it.
- Dedicated public-only reads exclude private notes, contact fields, numerical capacity and attendance counts even for signed-in owners. Existing organizer reads retain private management data.
- `public_information` is optional plain text on series and events. Events inherit an editable snapshot at creation; explicit clearing never falls back to current series text. Existing rows remain empty, never populated from private notes.
- Venue maps are single-pin, read-only Leaflet/OpenStreetMap maps loaded only after Show map. Google Maps/Apple Maps driving links use the saved destination without requesting browser location. Public map discovery remains deferred.
- Event capacity is now a **soft suggested attendance limit**, superseding earlier hard online-registration capacity rejection and kiosk-capacity exemptions. Capacity never blocks registration or confirmation; other eligibility, duplicate protection and manual closure rules remain unchanged. Configurable capacity plan limits remain enforced independently.
- Estimated attendance counts confirmed, non-deleted registrations once, plus an organizer-maintained audience guest count excluding performers. Hidden identities still count. A registration with no non-deleted sets counts; one with sets counts unless all are cancelled/no-show. Claims and additional sets do not multiply attendance.
- Audience count starts at zero for new events and is not copied; existing events have unknown audience attendance until recorded. Audience-only edits are operational and do not require replacing retired city references.
- Public status is at-capacity, below-limit or incomplete, never a seating guarantee. Known performers alone can establish at-capacity with unknown audience count. No public numerical counts or remaining places are shown. At-capacity warns about possible difficulty finding seating or performing without disabling registration.

## Public series events and media browsing

- Public series pages have Events, Photos, and Videos tabs, defaulting to Events. Event and performer-profile galleries have Photos and Videos tabs, defaulting to Photos. There is no public All media option; both media tabs remain visible with explicit empty states. Profile gallery visibility and consent rules still apply.
- Events use server-side Previous/Next pagination with 10 items per page. Upcoming includes running events first, labelled "Happening now", then nearest future events; Past is newest first. Always-visible Year/Month filters use each event's venue-local start date; All years/All months are defaults and Month requires Year. Filter changes reset page 1.
- A separate public-only series-event browsing operation preserves the existing organizer events API. Public browsing never exposes drafts, including to owners.
- Featured media is series-only. Events shows a compact mixed showcase above the tabs; Photos/Videos show matching featured items first in organizer order, without grid duplication. Strips are manually browsed, not automatically rotating.
- Featured viewers preserve the active tab and browsing position; arrows stay in the featured selection. Explicit Browse all photos/videos and View event actions provide onward navigation. Filters, pagination, tab state and return position survive navigation.
- Selecting Events, Photos or Videos does not automatically scroll the page or restore a different per-tab scroll position. Browser Back/Forward still restores the browsing position.
- Media retains Newest/Shuffle sorting and hybrid cursor loading. Media-by-date, event and performer selectors remain deferred.
- Events retain only Draft/Published statuses and computed future/running/past phases. Series statuses are unchanged. Paused series and all their events/media are unavailable publicly, including derived profile galleries and media deep links/OG. This supersedes earlier paused-public gallery/directory descriptions. Organizer management access remains available; already-known raw CDN URLs are not revoked.

## Delivery order

- Phase 1 is organizer-first: create and manage open-mic series, create and operate events, manage rosters, and publish organizer-owned photos and video links.
- Performers can sign up, browse open-mics and events, and register in Phase 1.
- Phase 1 public surfaces are read-only for visitors and include the home, profile, open-mic, event, and registration pages.
- Performer-authored content, comments, reviews, reactions, private messaging, follows, and social discovery are deferred until later phases.

## Organizer event creation

- Event creation retains the existing series-default path and allows an organizer to optionally choose at most 10 source events: up to five nearest upcoming and five most recent past events, filling unused slots by proximity to the current time.
- A visible public-series event offers a “Copy” action that preselects the event and prefills editable start/end date-times in the source time zone, including the full end date for overnight events. The organizer changes the date and time directly in “Starts at” and “Ends at”; there is no separate “New event date” field or date confirmation. Changing the start preserves the copied elapsed duration. The series-level create action and dashboard New Event flow may instead select a source event or continue with series defaults.
- Source event details copied as editable initial values are title, time zone, venue/location snapshot, capacity, activities, tags, notes, and entry-fee details. New events always start as drafts with registrations open; event roster/attendee data, media, IDs, links, QR codes, publication state, and registration-closure state are not copied.
- Without a source event, the end defaults to three hours after the start. Changing the start preserves the current duration by moving the end; changing the end updates the duration without changing the start.
- Copied date/time values are interpreted in the source event's time zone. Nonexistent or ambiguous local times at daylight-saving transitions require the organizer to select a different time; the application does not silently adjust them.
- Public-series creation and copy controls are shown only when the active organizer profile owns the series. API authorization remains authoritative.

## City catalogue and public discovery

- Home discovery starts within 50 km of browser location, falling back to a resolved saved account city. Both public sections use one origin/radius; searches never widen automatically.
- Explicit expansion targets at least 20 **additional** public series outside the current radius, up to 200 km. Suggest the smallest outward-rounded radius that reaches that target, including distance ties. If fewer exist, offer the actual additional count within 200 km; if none exist, do not show an expansion action.
- Suggested cities must contain active, non-deleted public series themselves, not merely listings within their catchment. Order cities by straight-line distance from the search origin and show country/region to disambiguate names.
- Choosing a city starts a 50 km search without changing account preferences. Three-card home previews link to `/discover`, with Open mics/Upcoming events tabs and numbered pagination. Series are nearest-first with an origin and alphabetical otherwise; upcoming-event time semantics are unchanged.
- Discovery overrides survive in-app navigation and Back/Forward, but reset on refresh/new app load. Without a usable origin, show general previews and explicit location/city actions, not purported nearby distances.
- City search uses a versioned, packaged JSON catalogue derived from the complete Simplemaps Basic `worldcities.csv`, preserving stable source IDs, Unicode/ASCII names, ISO country codes, region, centre, capital metadata and nullable population. JSON is validated once at API startup and is the search authority; search values are not compared with the database copy. Results are bounded, rank exact city matches before prefixes and other city/country matches, then population and stable ties. Retired entries remain resolvable by ID and eligible for public discovery when they have public series, but are excluded from autocomplete.
- The PostgreSQL cities table remains the UUID identity and foreign-key boundary for resolved references, saved-city reads and PostGIS calculations. An explicit maintenance import synchronizes JSON fields into the database by stable source identity without changing existing UUIDs; API startup does not import or compare catalogues. JSON candidates are mapped to UUIDs by source identity at search time. If a matching JSON city has no database identity, search fails explicitly with an import-required error rather than skipping results, returning a partial list or importing on demand. Temporary JSON/database differences are allowed: search uses JSON while saved details, selection validation and spatial calculations use the database until an explicit import.
- Every city-entry form uses shared autocomplete. Unmatched free text remains allowed and optional fields remain optional. A selected city supplies country; organizer free-text entry reveals a country fallback selector. Resolved geographic discovery and exact venue coordinates are separate concerns.
- Organizer city selection seeds an unconfirmed venue pin; an explicit confirmation or refinement is required before saving. Existing/inherited exact locations are not replaced merely by loading the form.
- Nullable selected-city references supplement, rather than replace, existing resource location snapshots. Catalogue refresh, account claims and profile adoption must not rewrite guest provenance or historic attribution. Ambiguous legacy names are not resolved by guessing the largest city.
- City-only LocationIQ search and provider-city caching/persistence are removed. LocationIQ remains behind the existing adapter for authenticated organizer address search and reverse geocoding, with its shared atomic daily budget and scheduling unchanged.
- City identity is stable and catalogue entries are retired rather than deleted. Retired city IDs remain readable and preserve saved references, historic text and provenance. Mutations that save resource details must select an active city or clear the reference using the resource's existing free-text/optional-city behavior, including a retired city inherited by a new event. Lifecycle-only operations such as status changes, check-in and registration closure do not require city replacement; mixed detail/lifecycle updates do. The API enforces this distinction.
- The supplied dataset is Simplemaps Basic, licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) according to its [edition comparison](https://simplemaps.com/data/world-cities). Convert the complete CSV once, verify all source identities and values, then maintain the versioned JSON directly; preserve attribution and describe the derivation and maintenance process in [the dataset notice](../licenses/worldcities.txt). Public pages credit Simplemaps and link to the source/licence. Commercial Pro/Comprehensive redistribution restrictions are not the Basic licence. Public map discovery, personalized recommendations and social discovery remain deferred.

## Handles

- Profiles and open-mic series share one global handle namespace.
- Canonical handles preserve owner-selected casing; lookup and uniqueness are case-insensitive.
- Case-only changes are allowed without limit, do not create redirect history, and redirect previous casing to the new canonical URL.
- Changes to any non-case character use the normal rename restrictions: 30-day redirect, 30-day quarantine, and auto-reclaim afterward.
- Owners retain the original guest registration provenance when a registration is claimed or later attributed to a profile.

## Profile kinds and handles

- Only performer profiles have handles. Organizer profiles never receive a handle; an organizer's public presence is its open-mic series, each of which has its own handle. This keeps a person's name (e.g. `@paul-dermody`) free for the performer profile they are likely to create later.
- Organizer profile pages (`/profiles/:id`) are reached by UUID only and list the series the organizer owns.
- Handles held by organizer profiles before this decision were hard-deleted by migration `017_remove_organizer_handles`, as a one-time exception to the redirect/quarantine policy, so they are immediately available.
- `profile_kind` is immutable after creation; `PATCH /profiles/{id}` does not accept it.
- An account cannot delete its currently selected profile (`409 CURRENT_PROFILE`) or its last remaining profile (`409 LAST_PROFILE`). Platform admins deleting another account's profile are exempt from the current-profile rule.
- Creating an open-mic series requires an active organizer profile. The create-series page does not create one implicitly; non-organizers are directed to create or switch to an organizer profile.
- The UI distinguishes profile kinds with a shared kind registry (icon + translated label) and a common profile identity component; kind is always shown as icon plus text, never color alone.

## Guest Registrations

- Guest registrations may be claimed at any time during or after the event.
- Claiming is explicit and requires a verified email match.
- Adoption of a claiming profile is an explicit public-attribution choice and may be changed later by the registration owner.
- The claim request identifies the adopted profile explicitly (`adopted_profile_id`), since an account may own more than one performer profile.
- A duplicate guest registration is defined as a second row for the same event with the same verified contact email; unverified/pending rows do not block others until confirmed. Enforced by a partial unique index on `(event_id, lower(contact_email))` where `email_verified_at IS NOT NULL`.
- A registration claim is atomic: the first successful claim wins, and a losing concurrent claim attempt fails explicitly with `409` rather than silently overwriting or duplicating attribution.
- Media consent is retroactive. Revocation blocks new media attribution to the registration and immediately removes already-attributed media from application listings, profile galleries, the canonical `/media/:mediaId` page, and media-specific Open Graph output. It does not invalidate an already-known raw CDN object URL. Affected media enters the standard 30-day soft-delete window; restoring consent during that window automatically restores media deleted solely because of that revocation. Media that was independently soft-deleted stays deleted. `Registration.media_consent_updated_at` records when consent last changed, for audit purposes.
- Guest registration submission is rate-limited per source (e.g. per IP) to deter abuse; exceeding the limit returns `429`.

## Organizer management actions

- Series and event management controls are grouped into hamburger menus on the dashboard, `/series/{id}`, and `/roster` pages so a single action surface covers navigation, lifecycle state changes, and sharing utilities without exposing inconsistent per-page toolbars.
- Series publish, pause, resume, and delete actions use modal confirmation dialogs before mutating API state. Event publish, unpublish, and delete actions follow the same confirmation pattern; closing event registrations remains a separate control and is not an event lifecycle state.
- Paused series can be soft-deleted through the same owner-scoped path as other organizer-managed resources, with a 30-day recovery window matching the uniform retention policy.
- Event lifecycle actions use the existing `PATCH /events/{id}` running-state behavior plus the existing soft-delete endpoint; copy-link and QR download actions are included in the same menu alongside those lifecycle actions.
- Copy-link actions use the `Copy` icon and QR actions use the `QrCode` icon across the surfaces that expose shared registration links.

## Forms and location picker

- React Hook Form + Zod is the standard for every form in `apps/web`, including forms that don't touch location (e.g. the profile editor). Shared per-form Zod schemas live near each page; shared cross-form pieces (e.g. `baseLocationFieldsSchema`) live in `apps/web/src/features/location.ts`.
- The venue/event location fields (map, address, latitude/longitude) are implemented once as a reusable `LocationPicker` component (`apps/web/src/components/location/`) plus a `useGeocoding` hook, embedded via any form that collects a location — today the OpenMic and Event forms, and any future form that needs one.
- Map rendering uses Leaflet + react-leaflet with public OpenStreetMap raster tiles (no API key required for the map itself), chosen over MapLibre/Google/Mapbox/OpenLayers per the comparison in [research/open-mic-map-location-picker.md](research/open-mic-map-location-picker.md).
- Geocoding (address → coordinates and reverse) uses LocationIQ, accessed only through a backend proxy (`GET /geocoding/search`, `GET /geocoding/reverse` — see [architecture/api-design.md#geocoding](architecture/api-design.md#geocoding)); the LocationIQ API key never reaches the browser.
- The backend proxy throttles outgoing LocationIQ calls to stay within the shared free-tier rate limit across all concurrent users, and returns a distinct `GEOCODING_RATE_LIMITED`/`GEOCODING_UNAVAILABLE` error the frontend can detect.
- On rate-limiting or provider failure, the frontend disables the address-lookup assist for the rest of the session and logs the event through a pluggable reporter (console-only for now; swappable for real telemetry later without changing call sites). The map's draggable pin and the always-present numeric latitude/longitude inputs keep working regardless — the assist is a progressive enhancement, never a requirement to submit a location.

## Media

- Organizer-owned media `source_url` is validated server-side: photos must be objects in the platform's own S3 media bucket (via the upload-url flow); videos must link to an allowlisted host (`youtube.com`, `youtu.be`, or `vimeo.com`). Arbitrary hosts are rejected.
- Organizers upload media only to events, registrations, and open-mic series, never directly to organizer profiles. A performer profile gallery is a derived view of event media linked to registrations that have adopted that profile.
- Performer attribution attaches media to a registration, not to an individual performance/set. Free-standing event and open-mic media has no registration link.
- `/media/:mediaId` is the sole canonical public URL for an individual media item, regardless of which galleries display it.

### Media delivery

- Photo bytes are served from a dedicated `media.openmics.org` subdomain backed by its own CloudFront distribution + S3 origin (OAC). The main site distribution carries only `/media/*` → ALB for OG-stamped SPA deep-links; it does not front the media bucket directly.
- The CloudFront ACM certificate in `us-east-1` covers the apex domain, `www`, and the single-label wildcard `*.<domain>`. The wildcard replaces per-service-subdomain SAN entries and covers the dedicated media hostname; it does not cover multi-label subdomains.
- Production releases are schema-first: build the web assets and release images, deploy the isolated migration task, review and apply pending migrations and import the packaged city catalogue, then deploy MediaStack, ApiStack, and FrontendStack in that order. The scheduled media purge worker must not activate before its schema exists, and new frontend assets must not precede the supporting API. Migrations and city import can share an ECS task but commit separately; import failure stops the rollout without undoing committed migrations.
- Media purge runs once daily as a one-off Fargate task in public subnets with a public IP, using the release API image and database secrets injected by ECS. This replaces the proposed VPC Lambda: the no-NAT VPC cannot give a Lambda public internet access merely by placing it in public subnets. Do not add NAT gateways or recurring-charge interface endpoints for this worker. The task processes records due at the start of the run in 500-row pages, without a total record cap, within a five-minute runtime limit. Rows are marked processed only after successful deletion; failures are logged and skipped for the rest of that run, remaining queued for the next daily run. Replacement, abandoned-upload and manual deletion records use the same daily queue.
- Video media is not re-hosted. Thumbnails are hotlinked from the provider CDN (`i.ytimg.com`, `vumbnail.com`); playback uses the provider iframe inside the lightbox.
- S3 object layout is flat per-media-id: `tmp/{accountId}/{uuid}.{ext}` (presigned-PUT target, 24h lifecycle), `original/{mediaId}.{ext}` (uploader's extension preserved), `renditions/{mediaId}/{thumb|grid|lightbox}.webp` (always webp; sharp converts). No entity-scoped (`events/...`) or hash-sharded layout. Objects are uploaded with `Cache-Control: public, max-age=31536000, immutable`.

### Organizer `DEFAULT_PLAN` values (Phase 1, config-only)

Shipped as a single hard-coded `DEFAULT_PLAN` object in the API; every organizer uses it. No `Plans` table and no `Accounts.plan_id` column in Phase 1 — introducing a second plan is a config change plus (then and only then) a migration.

The Plan **deliberately extends beyond media quotas**, overriding `media-gallery-design.md` §8.5 which scoped the Plan "narrowly to media quotas." Rationale: the Plan is where every tier-differentiating lever lives, and splitting media from non-media caps would double the surface for no gain. Media-only consumers of the Plan read only the media-related fields.

#### Media quotas (enforced in Phase 1)

- **Photo MIME allowlist:** `image/jpeg`, `image/png`, `image/webp`. Everything else is rejected at `POST /media/upload-url` with `MEDIA_UPLOAD_INVALID`. HEIC, AVIF, GIF, TIFF, raw formats, and video uploads are out of scope.
- **Max per-file photo size:** 10 MB (10,485,760 bytes). Enforced client-side as a friendly error and server-side both at `POST /media/upload-url` and in the presigned PUT `Content-Length` policy.
- **Per-event photo count cap:** 50 photos. Primary monetization lever: a sharp, visible ceiling tied to a successful night. Enforced at `POST /media` (commit). Returns `MEDIA_QUOTA_EXCEEDED` with `scope: 'event'`.
- **Per-event video count cap:** 50 videos. Mirrors the photo cap. Enforced at `POST /media` (commit) for `media_type='video'`. Returns `MEDIA_QUOTA_EXCEEDED` with `scope: 'event'`.
- **Global per-account byte backstop:** 5 GB (5,368,709,120 bytes). Ops safety net, not a conversion lever — set generously enough that no organic Phase 1 user hits it. Counted across every non-hard-deleted `original/*` object owned by the account. Returns `MEDIA_QUOTA_EXCEEDED` with `scope: 'account'`.
- **Presigned PUT URL expiry:** 15 minutes. Single-use, server-generated object key only (never client-supplied), bound to a specific `Content-Length` max and `Content-Type`.
- **AV scanning:** disabled. The Plan shape carries no `av_scan_enabled` flag; adding one is deferred until a scanning technology is chosen.
- **Rendition variants:** `thumb` (400px short side), `grid` (800px), `lightbox` (2048px), all webp. Fixed; not tunable per plan.

#### Capacity caps (enforced in Phase 1)

- **`max_series_per_organizer`: 1.** Counted across non-soft-deleted series owned by the organizer. Soft-deleted series free the slot immediately (permissive — lets organizers "reset" by deleting). Enforced at `POST /open-mics` with `PLAN_LIMIT_EXCEEDED` and `scope: 'series'`.
- **`max_events_per_series`: 50.** Lifetime cap: counts non-soft-deleted events (draft + published + past) across the series. Past events still count toward the cap — a long-tenured organizer who's run many free events eventually hits the wall, which is intentional conversion pressure. Enforced at `POST /open-mics/{id}/events` with `PLAN_LIMIT_EXCEEDED` and `scope: 'event'`.
- **`max_event_capacity`: 50.** Caps the maximum `capacity` value the organizer can configure on an event (`capacity > 50` or unlimited capacity are rejected on event create/edit). Does NOT change the Milestone 2 rule that kiosk sign-ups are exempt from the organizer-set capacity but still count toward it. Enforced at `POST /events` and `PATCH /events/{id}` with `PLAN_LIMIT_EXCEEDED` and `scope: 'event_capacity'`.

#### Reserved conversion-lever fields (shape only, not enforced until the underlying feature ships)

These exist in the Plan shape so a future Pro plan can gate them with a one-line config change. In Phase 1 they are either boolean false, numeric zero, or a string literal; the API ignores them (because the gated features don't exist yet).

- **`assistants_per_series`: 1.** Free tier allows one co-manager (beyond the owning organizer) per series; a future paid tier can raise this. Reserved for the deferred multi-admin collaboration feature — enforced when `SeriesAssistants` lands.
- **`custom_branding_enabled`: false.** Reserved for the "Powered by Openmics" footer / watermark removal lever. Enforced when branding configuration ships.
- **`custom_domain_enabled`: false.** Reserved for mapping an organizer-owned domain (e.g. `myopenmic.com`) to their series page. Highest-stickiness paid lever; typical top-tier offering in creator SaaS.
- **`analytics_tier`: `'basic'`.** Reserved; today's dashboard effectively is "basic". Pro tier value will be `'full'` (referral funnel, repeat-performer analytics, time-of-day heat). Enforced when the richer analytics surface ships.
- **`data_export_enabled`: false.** Reserved for CSV/JSON export of event registrations (classic Day-30 "I need my data" conversion moment).
- **`bulk_media_download_enabled`: false.** Reserved for a ZIP-of-all-event-photos download.
- **`calendar_invite_attachments_enabled`: false.** Reserved for real `.ics` attachments on performer confirmation emails (vs. the current plain-text body).
- **`email_sender_customization_enabled`: false.** Reserved for a custom from-name on performer emails (brand consistency lever).
- **`sms_reminders_enabled`: false.** Reserved for a Phase 2 Twilio-adapter SMS reminder sent to performers before their set.

#### Explicitly NOT in the Plan

- **Comments / likes / reactions per account.** These would be anti-abuse rate limits on performer actions, not organizer capability gates. Different concern, different owner. When commenting or reactions ship, add a dedicated "Platform rate limits" section to this document for per-account throughput caps that apply to **every** user regardless of tier. If paid tiers ever lift those limits, that'd be a separate `PerformerPlan` entity introduced then.
- **Soft-delete recovery window differentiation.** Would conflict with the uniform 30-day retention decision above.
- **Per-day event-create rate limits.** Users don't notice until it's too late to convert.
- **Expanded MIME types in paid tiers (HEIC, AVIF, GIF).** Low signal; users don't know their phone's export format.

### Media consent at kiosk

Both kiosk flows ask the performer explicitly for `media_consent` on their own form with the toggle **pre-checked to TRUE**. This deliberately deviates from design doc §10.2's "organizer-kiosk defaults true without asking, kiosk-QR asks without a default" split in favor of a single consistent, auditable pattern across both kiosk surfaces. [media-gallery-design.md](media-gallery-design.md) §10.2 should be reconciled to this record.

## Infrastructure

- **Infrastructure authority:** AWS CDK (TypeScript) is the infrastructure boundary. Code lives under `infra/` as its own package (own `package.json`/`tsconfig.json`, CommonJS — deliberately not part of the root `"type": "module"` workspace). `bin/infra.ts` is the CDK app entry; each bounded concern gets its own stack class under `infra/lib/` (e.g. `EmailStack`). This decision supersedes the older EC2-oriented infrastructure narrative until those architecture pages are rewritten.
- **API compute:** ECS Fargate (not EC2), because the API serves long-lived SSE connections (`GET /api/notifications/stream`), which rules out Lambda-behind-API-Gateway without a WebSocket re-architecture. Fargate keeps a persistent Node process without server patching/PM2/systemd.
- **Email:** SES, invoked only through an SQS queue + a Lambda consumer (never called synchronously from the API). The API's `EmailAdapter` (`apps/api/src/email/`) enqueues a JSON message; the Lambda in `infra/lib/lambda/email-sender/` sends it via SESv2. Failed sends retry via SQS and land in a dead-letter queue after 3 attempts. This part matches the original `infrastructure.md` design and is unchanged.
- **Cognito/Amplify:** Cognito remains the managed auth provider. The frontend uses the Amplify **client SDK only** for Auth (`aws-amplify/auth`). Frontend hosting, Cognito, S3, and all other AWS resources are provisioned via CDK.
- **CI/CD:** GitHub Actions with OIDC federation to AWS (no long-lived IAM access keys stored as repo secrets) for both application deploys and any future `cdk deploy` step.
- **Environments:** CDK stacks are namespaced per environment (`OpenMicEmailStack-dev`, `-staging`, `-prod`) via an `environmentName` context value/`OPENMIC_ENVIRONMENT` env var, starting in one AWS account; a harder account-per-environment split is deferred until team size or compliance needs justify the added overhead.
- Deployment/validation status: `cdk synth` has been run locally to validate the stack; nothing has been deployed to AWS yet (no bootstrap, no real resources exist).

## Retention

- Phase 1 soft-deletable records (profiles, open-mics, events, registrations, media) use one uniform window: 30 days recoverable, then hard-deleted by the purge job. This matches the handle redirect/quarantine cadence already in place.

## API Contract

- `openapi.yaml` is reduced to the Phase 1 executable contract. Reviews, comments, reactions, private messaging, suggestions, notifications, follows, multi-admin collaboration roles, public map discovery, and the legacy slug system are removed from the contract (not the product) and tracked as deferred surface in [architecture/api-design.md](architecture/api-design.md).
- Profile and open-mic updates use `PATCH` with a genuinely partial request body, not `PUT` with a full-replacement body.
- `Handle.status` and `Availability.reason` use the six-state model from [6-open-mic-vanity-urls.md](6-open-mic-vanity-urls.md): `current`, `redirect`, `quarantined`, `reserved`, `available`, `tombstoned`.
- The public vanity resolver (`GET /@:handle`) is intentionally outside `openapi.yaml`; it is served by Fastify directly, outside the `/api` base.

## Milestone 0 contract reconciliation

- **Event update/delete path:** the implementation moved to the flat `/events/{id}` path (`PATCH`/future `DELETE`), matching `openapi.yaml`, rather than keeping the nested `/open-mics/{id}/events/{eventId}` path the code had drifted to. The nested `GET /open-mics/{id}/events/{eventId}` read route is retained (it is not the mismatch that was flagged) alongside the flat `GET /events/{id}`; both resolve the event by UUID or `public_code`. `openapi.yaml`'s `updateEvent` operation is `PATCH`, not `PUT`, for the same partial-update reason as profiles/open-mics.
- **`/auth/sign-up`, `/auth/sign-in`, `/auth/refresh-token`:** removed from `openapi.yaml`. No frontend code called them; the browser talks to Cognito directly through Amplify. `GET /auth/profile` (implemented, aliases `GET /me`) is unaffected and remains.
- **`PUT /registrations/{id}` → `PATCH /registrations/{id}`:** changed for the same partial-update reason as profiles/open-mics/accounts. `PUT /accounts/{id}` (unimplemented, Milestone 1) is also corrected to `PATCH` in `openapi.yaml` while making this pass, since it is a genuinely partial update (`preferred_language`, `display_name`, `city`) and not a full-resource replacement. `PUT /accounts/{id}/current-profile` is intentionally left as `PUT`: it replaces a single pointer value wholesale, not a partial field set.
- **Media, reserved-handle admin, and edit-token rotation:** remain documented-but-unimplemented in `openapi.yaml`, previously assigned to milestones per the earlier plan (now [FEATURE-PLAN.md](FEATURE-PLAN.md)). `PATCH /accounts/{id}` is implemented for `display_name`, `city`, and `preferred_language`; profile-scoped `theme_name`/`color_mode` persistence and mandatory first-profile onboarding are also implemented.

## Milestone 1 authentication

- **ID token, not access token, is the bearer token `AuthVerifier` verifies.** The earlier plan (now [FEATURE-PLAN.md](FEATURE-PLAN.md)) originally said "access-token verification"; [5-open-mic-frontend-architecture.md](5-open-mic-frontend-architecture.md) says the client attaches the Cognito ID token. These conflicted; resolved in favor of the ID token, because only the ID token carries the verified `email` claim account provisioning needs, and the feature plan has been updated to match. The verifier rejects any token whose `token_use` isn't `id` (including access tokens) alongside malformed/expired/wrong-issuer/wrong-audience tokens.
- **Account provisioning is idempotent-upsert-on-first-request, not OAuth-callback/referral-attributed.** `architecture/data-model.md` and `architecture/api-design.md` describe a richer OAuth-callback provisioning flow tied to referral capture via a signed `state` value; that flow is scoped to Milestone 3 (referrals). Milestone 1's `findOrCreateAccountByCognitoId` provisions an account on first successful verification via `INSERT ... ON CONFLICT (cognito_id) DO UPDATE ... RETURNING`, with no referral attribution yet.
- **`is_platform_admin` is always read from the `accounts` table**, never trusted from a JWT claim, per `architecture/data-model.md` — Cognito ID tokens can remain valid up to an hour, and a revoked admin must lose access sooner than that.
- **Profile preferences and mandatory onboarding (item 6 redesign):** the earlier plan (now [FEATURE-PLAN.md](FEATURE-PLAN.md)) originally described account-level theme/color-mode preferences for `PATCH /accounts/{id}`, but `architecture/data-model.md`'s `Accounts` table has no such columns (only `Profiles.theme_name`). Resolved by keeping `theme_name`/new `color_mode` on `Profiles` (added via migration `010_profile_color_mode`), leaving `PATCH /accounts/{id}` scoped to `display_name`/`city`/`preferred_language` only (matching `AccountUpdateRequest`), and adding a mandatory frontend onboarding step (performer vs. organizer, plus theme/color-mode) that runs whenever a signed-in account has zero profiles, reusing `POST /profiles`. The same theme/color-mode picker is reusable at any profile-creation time, not just onboarding. See `architecture/data-model.md`'s "Onboarding and profile-scoped preferences" note.
- **Organizer route-level ownership check (item 8):** auditing the pre-existing per-page `isOrganizer` checks found they already relied on real server responses (`/me/permissions` and the account's own `/accounts/{id}/profiles` list) rather than any locally-trusted assumption, so no security fix was required for series/event listing pages. However, the open-mic and event edit forms (`OpenMicFormPage`, `EventFormPage`) checked only the role-level `profiles:manage` permission, not whether the specific resource being edited (`owner_profile_id`) belonged to the active organizer profile — an organizer could load another organizer's edit form by guessing/URL-sharing an id, though the API itself already rejected the eventual mutation. Both forms now additionally gate on `owner_profile_id === activeProfile.id` before rendering. The duplicated `isOrganizer`-check logic across five pages was also consolidated into one `useOrganizerProfile()` hook in `features/organizer.ts`.
- **`display_name`/`profile_name` defaults must never trust `cognito:username`.** A production bug surfaced a raw Cognito `sub` GUID as an account's `display_name` and, downstream, as the onboarding-created profile's `profile_name`. Root cause: `cognito-verifier.ts`'s display-name fallback used `payload['cognito:username']`, which for this user pool's email-alias sign-in configuration (no `name` attribute collected at hosted-UI sign-up) equals the raw `sub`. Fixed by dropping that fallback in favor of the email's local part (`payload.email.split('@')[0]`), and by making `OnboardingPage` always require the user to confirm/edit a suggested profile name and a suggested handle (with the same live availability check as `OpenMicFormPage`/`EventFormPage`, via `useHandleAvailability`) rather than silently submitting an unconfirmed default — a defense against any future bad default from any source. `POST /profiles` already accepted an optional `handle`; onboarding now always supplies one.
- **The organizer dashboard's "my series" list needs its own endpoint, not the public directory query with an ad hoc filter.** A production bug: after creating a series (default `status='draft'`), the organizer's own dashboard (`OrganizerSeriesPage`, `OrganizerEventsPage`) couldn't see it — the newly created series page rendered blank. Root cause: `useOrganizerOpenMics` called the public `GET /open-mics?owner_profile_id=...`, but `owner_profile_id` was never a documented parameter of that endpoint — it was an undocumented ad hoc addition that still inherited the public directory's `status NOT IN ('draft','ended')` filter (intentional and correct for the public directory itself; see `architecture/api-design.md`'s "Directory search & map endpoints" section). Fixed by adding an authenticated `GET /me/open-mics?owner_profile_id=...` endpoint, following the existing `GET /me/permissions`/`GET /me/registrations` account-scoped pattern: it verifies the caller owns the given profile and returns every non-deleted series regardless of status. The frontend's `useOrganizerOpenMics` now calls this endpoint instead, fixing both dashboard surfaces at once.
- **Handle auto-suggestion and submit-gating must not silently freeze/block on transient async state.** Two related bugs surfaced from real usage of `OpenMicFormPage`/`OnboardingPage`: (1) the auto-suggested handle stopped updating after the first keystroke in the name field, traced to an effect that both watched and conditionally overwrote the same RHF-managed field gated on `dirtyFields.handle` — a fragile, timing-dependent pattern; fixed by tracking "user has manually edited the handle" with a plain `useRef` set only from the handle input's own `onChange`, decoupled from RHF's internal dirty-tracking. (2) both forms disabled their submit button whenever the async handle-availability check hadn't resolved to exactly `'available'`, including transient `'checking'`/`'idle'` states, so any network hiccup silently and permanently blocked submission; fixed by only blocking on confirmed-bad states (`'unavailable'`/`'invalid'`) and trusting the server's existing `HANDLE_UNAVAILABLE` error response as the final authority, consistent with treating the server as authoritative over client-side hints elsewhere in the codebase.



- Phase 1 SSE is scoped to exactly one stream: the organizer/assistant event-roster stream, `GET /events/{id}/roster/stream`. There is no general account-level or notifications stream in Phase 1 (`/notifications*` remains deferred, see [architecture/api-design.md](architecture/api-design.md#deferred-later-phase-api-surface)); [5-open-mic-frontend-architecture.md §6](../docs/5-open-mic-frontend-architecture.md) is scoped to match.
- **Authentication:** `EventSource` cannot send an `Authorization` header. The client first calls authenticated `POST /events/{id}/roster/stream-token` (organizer/assistant of that event only) to obtain a single-purpose `stream_token` valid for 5 minutes, then opens `GET /events/{id}/roster/stream?stream_token=...`. Raw bearer tokens are never placed in a URL.
- **Event names:** `registration.created`, `registration.updated`, `performance.created`, `performance.updated`, `performance.deleted`, `performance.reordered`.
- **Ordering and missed-event recovery:** every emitted event carries a monotonically increasing `id:` field (per event scope) so the browser's native `Last-Event-ID` header drives resume-after-reconnect. If the server can't satisfy a given `Last-Event-ID` (expired/unknown, e.g. after a deploy), it sends a `resync_required` event instead of replaying; the client responds by refetching `GET /events/{id}/registrations` in full rather than assuming partial replay is safe.
- **Heartbeat:** the server sends an SSE comment ping every 15 seconds to keep the connection alive through intermediary proxies/load balancers and to let the client detect a silently-dead connection.
- **Multi-instance fan-out:** the API runs as multiple ECS Fargate tasks, so an in-process event emitter cannot reach a connection held by a different task. The server uses PostgreSQL `LISTEN/NOTIFY` (channel keyed by event id) so any task holding the SSE connection for that event is notified regardless of which task handled the write, without introducing a separate message broker for Phase 1.
- **Reconnect:** the client uses exponential backoff capped at 30 s, per [5-open-mic-frontend-architecture.md §6](../docs/5-open-mic-frontend-architecture.md).
- This contract is implemented in the API and frontend; reconnects use a full roster resync because PostgreSQL `NOTIFY` is not a durable replay log. Playwright coverage and staging validation remain open.

## Milestone 2 event lifecycle

- **Date-derived event lifecycle supersedes manual running controls.** `Events.running` and Start/Stop/Restart actions are retired. Events have explicit `draft`/`published` status, while `future`/`running`/`past` is derived from server time and `[starts_at, ends_at)`. Public visibility requires a published event in an active series. Public registration requires `pre_only` or `both`, an unended published event in an active series, and an open `registrations_closed_at`; toggling that field never changes roster performance states. Organizer-supervised kiosk registration remains available regardless of public publication, registration mode, closure, or phase, but future/past kiosk launches require a client-side event-date confirmation before the kiosk session opens.
- **Kiosk QR phone registration uses a presence token.** The kiosk's event QR code encodes `/events/{id}/register?kiosk=<token>`, where the token is minted by owner-only `POST /events/{id}/kiosk-registration-token` (HS256, `purpose: 'kiosk_registration'`, bound to the event, valid until the event's `ends_at`). A registration carrying a valid `kiosk_token` is treated as proof of presence: it bypasses registration mode (including `on_night_only` and `external`), publication, phase, and `registrations_closed_at` checks, but still enforces the duplicate-email rule. Kiosk sign-ups — both organizer-typed kiosk-form entries and kiosk QR sign-ups — are exempt from event capacity, yet still count toward it, so regular online sign-ups remain blocked once the event is full. Such sign-ups are recorded with `submission_channel = 'kiosk_qr'` and `verification_method = 'kiosk_qr'` (or `authenticated_account` when a signed-in performer profile is used), are verified immediately with email optional, start in the `present` performance state, and receive no edit or confirmation email. `GET /events/{id}?kiosk_token=` returns the event even when unpublished so the phone page can load. Roster-stream tokens carry `purpose: 'roster_stream'` and each verifier rejects the other purpose. The durable series QR is unchanged and still shown only for `pre_only`/`both`. Tokens are not revocable; a shared copy of the QR works until the event ends (accepted trade-off).
- **Event soft-delete/recover implemented as flat per-table columns, not the unified `Deletions` journal table.** `architecture/data-model.md` describes an eventual unified deletions/recycle-bin journal, but no migration for it exists yet, and the already-shipped `performances` soft-delete (Milestone 0) did not build one either. `DELETE /events/{id}` (soft delete: sets `deleted_at`, `deleted_by_profile_id`, `recovery_deadline = now() + 30 days`) and `POST /events/{id}/recover` (restore: clears those three columns, only while `recovery_deadline > now()`) follow that same narrow, per-table precedent for consistency. Building the shared journal table remains open for whenever a cross-resource recycle-bin UI is actually needed.
- **Close/reopen registration needed no new endpoint.** It's already fully covered by the generic `PATCH /events/{id}` endpoint's nullable `registrations_closed_at` field; `EventFormPage` already has a "Close registrations now" action, and clearing the field reopens registration. No separate `close`/`reopen` operation was added.
- **Organizer roster (item 2) reuses the existing per-registration performance CRUD rather than adding new endpoints.** `POST /performances`, `PUT /performances/{id}`, `DELETE /performances/{id}` (Milestone 0) already cover create/edit/soft-delete with organizer-ownership checks; the only gap was listing. `GET /events/{id}/registrations` (organizer-only) now embeds each registration's `performances` (including organizer-only `notes`) via a batched lookup, avoiding an N+1 query per roster row. The frontend `EventRosterPage` (`/dashboard/series/{seriesId}/events/{eventId}/roster`) renders provenance badges (pending/verified/kiosk, derived the same way as the server's "publicly visible" rule), capacity/closure summary, filters, and per-performance sequence/status/notes controls (a plain number input for explicit sequence editing, per the plan's "sequence... or explicit sequence editing" alternative — no drag-and-drop reorder was built).
- **Kiosk registration (item 3) needed no backend changes.** `POST /events/{id}/registrations` already fully supported `organizer_supervised: true` + `submission_channel: 'kiosk'` (Milestone 0): it requires only `performer_name` (no contact email), sets `verification_method: 'organizer_kiosk'` and an immediate `email_verified_at`, and skips the confirmation-email flow entirely. The new frontend `KioskPage` (`/dashboard/series/{seriesId}/events/{eventId}/kiosk`, linked from the roster page's "Open kiosk" button) is a dedicated dark, high-contrast, large-touch-target form that requires only the performer's name, resets and refocuses itself right after each successful add (with a brief on-screen confirmation, no page reload), and surfaces closure/capacity/duplicate/forbidden errors with kiosk-specific copy. (Superseded for capacity: kiosk sign-ups are now exempt from capacity; see the kiosk QR bullet above.)
- **Roster redesign: performances are no longer a separate concept from performers in the UI.** Every registration now gets its first `Performances` row auto-created in the same transaction as the registration itself (status `present` for kiosk sign-ups, `registered` otherwise), so a "performer card" on the roster page is really just a performance row with its registration's contact/provenance info attached — organizers never see a bare registration with zero performances. `Performances.status` grew from 4 values to a 7-state lifecycle: `registered -> present -> scheduled -> performing -> performed`, plus `no_show`/`cancelled` as manual overrides from any state. Four new nullable timestamp columns (`checked_in_at`, `scheduled_at`, `started_at`, `finished_at`) are stamped automatically (server clock only, never client-supplied) whenever a row's status is set to the corresponding value, on both create and update. A performer doing a second set is **always a brand-new `Performances` row** (never the old row looping backwards), typically starting at `present` since they're already known to be at the venue — this preserves full history of every set played instead of overwriting it. The roster page displays a Kanban board (one column per forward state) on large screens and a single filterable list on small screens, with one primary action button per card (Check in / Schedule / Start / Finish) that always maps to exactly one status write.
- **Kiosk exit PIN: one server-side PIN per series, stored in plaintext by explicit product choice, with explicit owner-triggered reveal.** The kiosk page runs fullscreen when supported and requires the configured series PIN to exit back to the roster/dashboard. There is no per-session or client-only PIN. The PIN is configured per open-mic series and stored as plaintext in `open_mics.kiosk_backup_pin` via dedicated `GET`/`PUT /open-mics/:id/kiosk-backup-pin`, `POST /open-mics/:id/kiosk-backup-pin/verify`, and `POST /open-mics/:id/kiosk-backup-pin/reveal` endpoints. All endpoints remain owner-authenticated; routine status and verification responses expose only booleans, and the PIN is excluded from `serializeOpenMic`'s output, including public `GET /open-mics/:id`. The saved PIN is returned only by the explicit reveal endpoint, which sets `Cache-Control: no-store`; the frontend fetches it only after the owner selects Show PIN and clears its local copy when hidden or when replacement editing starts. This is deliberately not an account-security credential, but plaintext storage and explicit readback increase exposure to database access, operators, backups, and an owner's active session; request bodies must not be logged, reveal responses must not be cached, and database access should remain restricted. Migration 016 drops legacy hashes because they cannot be converted, so every previously configured series must set a replacement PIN after deployment. The kiosk exit uses four auto-advancing digit fields and verifies automatically after the fourth digit, without requiring a submit button or Enter key. The server PIN survives across devices/browsers running the same series. It remains a device-convenience lock, not an account-security boundary — any signed-in organizer can independently open their own kiosk session for the same event.
- **Historical manual-stop behavior (superseded).** The earlier `Events.running` stop/restart flow, its registration closure, and its bulk roster mutations are retired by the date-derived lifecycle decision above. Registration closure now changes only `registrations_closed_at`; organizers manage performance statuses explicitly through the roster.
- **Live roster updates (item 4) use PostgreSQL `LISTEN`/`NOTIFY`, not a persisted event log.** `POST /events/{id}/roster/stream-token` mints a 5-minute HS256 JWT (new `STREAM_TOKEN_SECRET` config value, with an insecure dev/test default) because `EventSource` cannot send an `Authorization` header. `GET /events/{id}/roster/stream` verifies that token, then `LISTEN`s on a per-event channel (`roster_<eventId-without-hyphens>`, kept alphanumeric so the unparameterizable `LISTEN`/`UNLISTEN` statements stay injection-safe) and forwards lightweight NOTIFY payloads (event name + id only, no row data) as SSE events with an incrementing `id:`. `registrations/routes.ts` and `performances/routes.ts` call a shared `notifyRoster` helper after every create/update/delete. **No durable replay log is kept**: since NOTIFY payloads are fire-and-forget and Postgres does not retain them, any reconnecting client that sends a `Last-Event-ID` header always receives an immediate `resync_required` event (telling it to refetch `GET /events/{id}/registrations` in full) before live-tailing resumes — there is no partial/incremental catch-up. This means every reconnect (page backgrounded, laptop sleep, brief network blip) costs one full roster refetch instead of a small diff; multi-instance fan-out (ECS Fargate) works because NOTIFY is broadcast to every listening backend connection regardless of which instance handled the client's request. This was implemented without a follow-up confirmation from the user; if reconnects turn out to be frequent enough in practice for the extra refetch cost to matter, revisit with a small ring-buffer replay log per event.
- **Kanban board is restricted to board-eligible registrations; pending ones get a separate simple list, and "claimed" was dropped from roster filtering entirely.** Per explicit user direction, the roster's per-card Kanban/list only shows registrations that are verified (self-registration, `email_verified_at` set) or kiosk (`organizer_supervised`) — a registration still awaiting email confirmation isn't board-eligible yet, so its performances are excluded from the board/mobile-list data entirely rather than just filtered out visually. Pending registrations instead render in a plain "Pending confirmation" `<ul>` (`PendingRegistrationRow`: name + Details/Edit only, no move controls, no kanban card styling) shown above the board. The provenance filter bar is now `All | Pending | Verified | Kiosk` — selecting "Pending" hides the board and shows only that list; the other three filter the board itself. `claimed_by_account_id` is a separate attribution concept (which account a registration is linked to) that doesn't affect roster eligibility or lifecycle, so it was removed from `provenanceOf`/the filter bar; it's still fully readable via `GET /registrations/{id}` and the registration-edit/details modals for anyone who needs it, just not roster-facing.
- **Roster "Delete" card action added a new `DELETE /registrations/{id}` endpoint (soft-delete, organizer-only).** No such endpoint existed before this change even though `registrations.deleted_at`/`deleted_by_profile_id`/`recovery_deadline` columns were already in the schema (migration 002). It mirrors `softDeleteEvent`/`softDeletePerformance`'s 30-day recovery window exactly, and deliberately uses the stricter event-owner check rather than `assertRegistrationAccess`, since the registration's own claimed-by account should not be able to delete it — only the event's organizer (or a platform admin) can. The frontend only offers "Delete" from the Registered column's card menu (before anything else has happened to that performer), behind a confirmation modal — once someone's checked in, been scheduled, performed, or marked no-show, deleting isn't offered; "No-show" is the equivalent action for that history-preserving case instead.
- **Roster page's "Stop registrations" button reuses the existing `PATCH /events/{id}` `registrations_closed_at` field (no new endpoint), same mechanism already described above for `EventFormPage`'s "Close registrations now" action.** The organizer can reopen registrations from either surface by clearing the nullable field; the control toggles between stopping and reopening without changing existing registrations or performances.
- **Moving a performer into "scheduled" auto-assigns the next event-wide `sequence` number server-side, instead of leaving it unset.** Previously, drag/move actions only ever sent `status` in the `PUT /performances/{id}` body, so `sequence` (already `ORDER BY sequence ASC, created_at ASC` in every roster query) stayed at its create-time value/`null` for everyone — meaning "who's up next" wasn't actually deterministic across organizers/devices, it just happened to match registration order. Now, when a `PUT /performances/{id}` sets `status: 'scheduled'` and the client didn't explicitly send a `sequence`, the server computes one itself (`nextSequenceForEvent`: `MAX(sequence)` across the event's non-deleted performances, `+1`) and stores it alongside the status change. Because ordinary status-only updates never touch `sequence`, that number is carried unmodified through `performing`/`performed`, so it doubles as the eventual play-order record — matching the request that "scheduled order and performance order... could be the same column." This is a best-effort (not fully serializable) counter: two organizers scheduling different performers in the same instant could theoretically compute the same next value before either write commits; given the low concurrency of this action in practice, that race was accepted rather than adding transaction-level locking.
- **Kanban board redesign: per-column sequencing, uniform delete-cascades-to-registration, and stricter movement rules — supersedes the "event-wide sequence" and "delete only from Registered" bullets above.** Per explicit user direction, refined the roster board as follows:
  - `sequence` is now scoped per status column instead of event-wide: `nextSequenceForColumn` computes `MAX(sequence)+1` within "present" or "scheduled" only (or `1` if that column is empty), replacing the old single event-wide counter. A performance is auto-assigned a bottom-of-column sequence whenever it enters "present" or "scheduled" without an explicit `sequence` — this covers both organizer moves and kiosk sign-ups (which land at the bottom of "present"). "performing" and "performed" don't carry a meaningful sequence at all (performed order is implied entirely by `finished_at`); "registered" cards are shown in registration order. Reordering (swapping two cards' `sequence`) is now rejected by the API unless the card's current status is "present" or "scheduled" — it is no longer possible to reorder within "performed".
  - **Delete now applies uniformly to a card in any column, not just "Registered".** Deleting a performance's card soft-deletes just that `Performances` row, unless it is the registration's only remaining (non-deleted) performance, in which case the API also soft-deletes the parent `Registrations` row in the same request (the performer would need to register again for a future set). The confirmation modal's copy distinguishes these two outcomes ("delete this performance" vs. "delete the registration") based on whether the registration has other performances. The DELETE handler runs the cascade check and any cascade delete *before* sending its response (not fire-and-forget afterward), so an immediate follow-up GET from the same client can't race ahead and see stale, non-cascaded state.
  - **Movement is restricted at both ends of two columns.** Only the "scheduled" card with the lowest `sequence` (top of the queue) may transition to "performing" — enforced server-side via a `topOfScheduled` lookup, not just hidden in the UI. Only the "performed" card with the latest `finished_at` may move out of "performed" to any other status (`lastPerformed` lookup) — covering the "moved to performed by mistake" fix-up case while leaving history-preserving order intact for everyone else already performed.
  - **Two timestamp special cases were added to the "stamp on entering status" default.** "performed" -> "performing" preserves `started_at` (it's the same set resuming, not a new one) and clears `finished_at`; "performing" -> "scheduled" (moved back a stage) clears both `started_at` and `finished_at`.
  - **Historical event-stop cleanup (superseded).** The old stop-time bulk no-show and deletion behavior no longer applies; date-derived phase changes do not mutate performances.
  - `registration.deleted` was added to the frontend's `ROSTER_STREAM_EVENTS` list (it already existed as a server-emitted SSE event name from the original `DELETE /registrations/{id}` work, but the roster page wasn't listening for it) so other open tabs refresh when a cascade-delete removes a registration.
- **Fixed duplicate roster GET requests on every organizer-initiated change.** Every roster mutation (`useUpdatePerformance`, `useCreatePerformance`, `useUpdateRegistration`, `useDeleteRegistration`, `useDeletePerformance`, `useCloseRegistrations`) already invalidated the roster query in its own `onSuccess`. But the exact same change also arrives back over the roster's own SSE stream a moment later (Postgres NOTIFY is broadcast to every listener, including the tab that made the change), which invalidated the query a *second* time — two GETs for one edit. Fixed by having each mutation mark its target query key as "self-caused" in `onMutate` (before the request round-trip, since the NOTIFY can race ahead of the HTTP response) via a small in-memory `Map` (`markSelfCausedChange`/`consumeSelfCausedChange` in `features/organizer.ts`, keyed by `roster:<eventId>`/`event:<eventId>`, one-shot with a 5s expiry); the SSE handler consumes that mark instead of invalidating when it sees the matching event. `resync_required` and the on-error reconnect catch-up path deliberately bypass this suppression (via a separate always-unconditional `invalidateRoster`), since those exist specifically to catch up on changes this tab might not already know about.
- **Removed the "Claim all" bulk action from `/claim-registrations`.** Per explicit user direction, `ClaimableRegistrationsPage` now offers only the per-row **Claim** action; the row that let a user claim every match at once (defaulting them all to the account's first performer profile) was dropped, since each guest registration should have its adopted profile chosen explicitly. `docs/5-open-mic-frontend-architecture.md` and `architecture/data-model.md` are updated to describe only the per-row action; no API change was needed since `POST /registrations/{id}/claim` was always per-registration.
